# InkPaw 开源发布约束

> 状态：生效（首次公开发布前约束）
> 建立日期：2026-07-15
> 适用范围：从私有开发仓 `inkstone_dev` 向公开仓 `InkPaw` 发布的代码、文档、测试、示例和二进制产物

本文档是发布门禁，不是对项目开源许可证的替代，也不构成法律意见。出现权属、客户数据或第三方许可疑问时，默认不发布，直到问题被明确。

## 1. 仓库模型

1. `inkstone_dev` 是私有开发仓，可保留运维记录、未发布设计、内部待办和完整开发历史，必须继续保持 private。
2. `InkPaw` 是独立公开发行仓，从审核过的当前快照建立，不保留私有仓 Git 历史。
3. 禁止将私有仓直接改为 public；禁止将私有仓的 `.git/` 、bundle、tag 或历史分支推入公开仓。
4. 公开仓的首个发行提交必须是已清理快照；此前只能保留干净的仓库初始化文件（如 LICENSE），提交信息不得包含私有部署、客户或协作者信息。

## 2. 权属边界

只有同时满足以下条件的内容才能发布：

- 发布者确认拥有代码和文档的著作权，或已获得明确的再分发授权。
- 不包含公司源代码、内部文档、客户交付物、商业模板、未公开接口或受限数据。
- 不包含从公司项目直接复制、轻度改写或无法说明来源的实现。
- 第三方文件的许可条件允许再分发，且已保留必要的版权和归属声明。

`reference/` 中的历史报告代码、工程数据和旧实现不属于公开发行物，无论其当前是否被调用，一律不得进入公开仓。

## 3. 首发允许清单

首个公开版本只从下列范围选择文件：

- `src/`：MCP 协议层、服务层、校验、转换、渲染、存储和 Markdown 支持。
- `test/`：不包含现实业务数据的单元、集成和视觉基线测试。
- `presets/`：通用样式预设，不得使用客户品牌、公司标识或商业模板。
- `examples/`：仅使用虚构或公开数据的最小可运行示例。
- `playground/`：经过品牌、隐私和安全边界清理的本地体验入口；默认仅监听 loopback，不包含公网部署配置。
- `scripts/`：不包含本机绝对路径、私有服务器或凭证的通用验证工具。
- `schemas/`：只在再分发条件确认后纳入，并在第三方声明中记录来源和本地修改。
- `docs/`：经重写的公开设计、使用、兼容性和贡献文档。
- `README.md`、`package.json`、`package-lock.json`、`.gitignore` 和已清理的 GitHub Actions workflow。

私有仓的 `webchat/` 不得原样复制。若迁移为公开 `playground/`，必须完成品牌清理、模型凭证处理、多用户隔离、测试和本地安全边界审核；公网部署仍须另行完成 SSRF、限流、滥用防护、来源控制和数据保留设计。

## 4. 禁止发布清单

以下内容不得出现在公开仓的当前文件、Git 历史、Issue、Actions 日志、Release 附件或截图中：

- `reference/`、`data/`、数据库、WAL/SHM、用户上传文件、生成的 DOCX/PDF/PNG 和备份。
- `.env*`、token、API key、恢复码、cookie、私钥、证书、连接串和鉴权请求头。
- 生产域名、IP、主机名、SSH 配置、开发者本机绝对路径、PM2 实例状态、反向代理实况和 DNS/Cloudflare 故障细节。
- 协作者真实姓名、内部分工、私人对话、会话数量、真实文档 ID 和用户行为记录。
- 客户、工程、桥梁、银行或公司名称，以及可重新识别现实对象的传感器布置和报告数据。
- `docs/deploy-webchat.md`、私有开发日志、运维交接、事故复盘原文、实时待办和带有本机/服务器状态的 Agent 指令文件。
- 未经许可的字体、图片、商标、模板和第三方大段代码。

若不能判断某文件是否安全，不使用“先发布再删除”策略，而是先排除。

## 5. 许可证与第三方内容

1. 公开仓默认采用 MIT License；最终发布前由版权持有人确认。MIT 允许个人和公司使用、修改、分发、再许可和销售软件，下游须保留版权和许可声明。
2. 根目录必须包含完整英文 `LICENSE` 文本及正确的版权年份/持有人，不得自行增删或改写 MIT 条款。
3. 根目录必须包含 `THIRD_PARTY_NOTICES.md`，列出再分发文件、依赖、来源、许可证和本地修改。仅当第三方许可证要求或项目需要额外归属时添加 `NOTICE`。
4. `schemas/ooxml/` 必须明确记录 ECMA-376 / python-docx 来源、获取日期和对 `schemaLocation` 的本地修改。在再分发权利未确认前，不得进入公开 Release。
5. `package.json` 应填写 `license`、`repository`、`bugs`、`homepage` 和作者信息。若暂不发 npm，可保留 `"private": true` 作为防误发布门禁，这不影响 GitHub 仓库开源。
6. 不得引入与项目对外许可证冲突的代码或素材；新增依赖时同步审查其许可证。

## 6. 公开文档约束

- README 必须先说明问题、设计哲学和最小可运行流程，不使用无法验证的性能或兼容性宣称。
- 所有示例必须可在全新目录按文档复现，不依赖作者本机目录、私有服务或预置数据库。
- 部署文档只能使用 `example.com`、环境变量和占位路径，不保留任何真实生产拓扑。
- 私有设计日志应重写为稳定的 ADR/设计文档，不直接搬运按日期累积的待办和故障处理过程。
- 可以保留通用的失败案例和技术取舍，但必须对人员、环境、数据和时间线去识别化。

## 7. 安全与隐私门禁

每次首发或重要 Release 前必须完成：

1. 通过文件清单审查确认禁止目录未进入 Git。
2. 扫描当前文件与公开仓全部历史中的 secret、域名、IP、邮箱、绝对路径和现实项目关键词。
3. 确认 `.gitignore` 至少覆盖 `.env*`、`data/`、`*.db*`、`*.sqlite*`、`*.docx`、`*.pdf`、预览图、日志、coverage 和临时目录。
4. 在 GitHub 开启 secret scanning 和 push protection（若账户/仓库支持）。
5. 公开仓新增 `SECURITY.md`，明确漏洞私下报告途径；未修复漏洞不得先在公开 Issue 披露可利用细节。
6. 不使用真实 token 做测试。即使凭证已过期，也按敏感信息处理。

## 8. 质量门禁

公开仓首发前必须满足：

- 在全新 clone 中能够执行 `npm ci` 和 `npm test`。
- GitHub Actions 使用公开环境可安装的依赖，工作流不得引用私有 runner、secret 或真实部署主机。
- CI 至少在 pull request 上运行核心测试；如完整 LibreOffice 集成测试成本过高，可拆分快速必跑与手动完整验证。
- README 中的 MCP 配置、CLI 命令和示例至少人工从零跑通一次。
- 测试失败、来源不明、发现敏感内容或第三方许可未确认时，Release 立即中止。

## 9. 开源后给公司使用

在项目权属和许可证已确认的前提下，公司可以作为下游用户使用公开版 InkPaw。建议采用以下边界：

- **公开上游**：通用 MCP 工具、渲染、校验、样式机制、存储接口、通用测试和文档。
- **公司私有下游**：客户模板、业务数据、内部鉴权、部署配置、系统集成、品牌资产和专有功能。
- 公司应按发布 tag/commit 锁定上游版本，保留 lockfile，不直接跟随公开仓未发布分支。
- 通用 bug 修复和可复用能力可考虑回馈上游；客户或公司特有实现保留在私有下游。
- 不得在公开 Issue 中粘贴公司日志、文档、数据库、配置和客户复现文件；应先构造去识别化的最小复现。

重要权属规则：开源之后，使用公司时间、设备、数据或业务需求产生的新改动，不自动属于个人可对外贡献的代码。将这类改动提交回公开上游前，必须根据劳动合同、公司制度和具体任务确认权属并取得必要授权。

## 10. 贡献与发布流程

### 首次发布

1. 在 GitHub 建立 `InkPaw` 公开仓。如已经有干净的 LICENSE 初始提交，保留该提交并将发行快照作为下一个提交；不得导入私有仓历史。
2. 从私有仓工作树按允许清单导出到新目录，不复制 `.git/`。
3. 删除禁止项，将历史日志重写为公开文档，将所有样例替换为虚构数据。
4. 添加 LICENSE、第三方声明、SECURITY、CONTRIBUTING 和公开 README；存在额外归属要求时再添加 NOTICE。
5. 完成安全、许可、文档和质量门禁后，创建单一干净迁移提交，并在 `SOURCE_SNAPSHOT.md` 记录来源提交。
6. 推送后再次从 GitHub 公开视角检查文件、Actions 日志、历史和 Release 附件。

### 后续同步

- 不对私有仓和公开仓做无审核的整分支 merge。
- 以经过审查的小批量 patch/cherry-pick 或重写提交同步通用变更。
- 从公开仓回合私有仓的外部贡献，也必须经过代码、许可和安全审查。
- 初期采用 Developer Certificate of Origin（DCO）式的 `Signed-off-by`。只接受贡献者有权提交的内容；在没有实际需求前不引入复杂 CLA。

## 11. Release 最终检查表

- [ ] 公开仓不含私有仓历史。
- [ ] `reference/`、运行时 `data/` 和私有 `webchat/` 部署材料未进入首发版本。
- [ ] `playground/` 默认只监听 loopback，且已明确标注不应直接公网部署。
- [ ] 无客户/公司数据、人员信息、生产环境和敏感凭证。
- [ ] 所有示例均为虚构或公开数据。
- [ ] LICENSE、THIRD_PARTY_NOTICES、SECURITY 和 CONTRIBUTING 已完成；若必要，NOTICE 已完成。
- [ ] OOXML Schema 的来源、修改和再分发权利已确认。
- [ ] `npm ci` 和 `npm test` 在全新 clone 中通过。
- [ ] GitHub Actions 不依赖私有资源，日志不泄露环境信息。
- [ ] README 的安装、配置、建档、修改和渲染最小流程已从零复现。
- [ ] 公开仓页面、历史、Issue 模板和 Release 附件已从匿名访客视角复查。

任一检查项不满足时，不进行公开发布。
